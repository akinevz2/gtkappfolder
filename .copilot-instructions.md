# GtkAppFolder - GitHub Copilot & LLM Maintenance Instructions

## Project Overview

**GtkAppFolder** is a modern GTK-based AppImage browser and launcher with the following characteristics:

- **Primary Language**: C++ (C++17 with `std::filesystem`)
- **Build System**: CMake 3.15+
- **Two Active Branches**:
  - `main` (GTK3 stable version)
  - `gtk4-libadwaita` (GTK4 modern version with libadwaita)
- **Key Dependencies**: GTK (3 or 4), GLib/GIO, libadwaita (GTK4 only), GSettings

### Current Architecture

```
src/
├── main.cpp              # Entry point, GtkApplication lifecycle
├── AppImageBrowser.h     # Class declaration, member variables, callbacks
└── AppImageBrowser.cpp   # Core implementation (~1150 lines)

CMakeLists.txt           # Build config, pkg-config linking
schemas/
└── com.github.gtkappfolder.gschema.xml  # GSettings schema for preferences
README.md                # User documentation
```

## Branch Maintenance Guidelines

### GTK3 Branch (`main`)

**Status**: Stable, feature-complete
**Toolkit**: GTK 3.0, GLib 2.0

**Key APIs in Use**:
- `gtk_box_pack_start()` / `gtk_container_add()` for widget hierarchy
- `gtk_widget_destroy()` for cleanup
- `gtk_entry_get_text()` / `gtk_entry_set_text()` for text input
- `gtk_drag_dest_set()` with `gtk_selection_data_get_data()` for DnD
- `GtkFileChooserDialog` (blocking dialogs)
- `gtk_menu_popup_at_pointer()` for context menus
- `gtk_message_dialog_new()` for alerts

**Maintenance Rules**:
1. **Do NOT apply GTK4 APIs** to this branch
2. When fixing bugs, test on GTK3 first
3. Use only GTK3-compatible GLib/GIO APIs
4. Keep signal connections using old `gtk_signal_connect()` patterns

---

### GTK4 Branch (`gtk4-libadwaita`)

**Status**: Under development, modern UI
**Toolkit**: GTK 4.0+, libadwaita 1.0+, GLib 2.0+

**Key APIs in Use**:
- `gtk_box_append()` / `gtk_flow_box_append()` (no packing, direct append)
- `gtk_widget_unparent()` for cleanup (not destroy)
- `gtk_widget_set_visible()` instead of `gtk_widget_show()`
- `gtk_editable_get_text()` / `gtk_editable_set_text()`
- `GtkDropTarget` with `on_drop()` callback (GValue-based)
- `GtkFileDialog` (async dialogs)
- `GtkPopoverMenu` with `AdwAlertDialog` for dialogs
- `GtkGestureClick` for button events (replaces button-press-event)
- `AdwApplicationWindow` + `AdwHeaderBar` for modern header

**Maintenance Rules**:
1. **Do NOT use GTK3 APIs** in this branch
2. Use `gtk_widget_get_next_sibling()` for child iteration (not GList)
3. All child management uses `gtk_widget_unparent()` (not destroy)
4. Dialogs are async; use callbacks/closures for results
5. Margins via `gtk_widget_set_margin_*()` (not border_width)

## Planned Modularization

### Current State (Monolithic)

All functionality is in `AppImageBrowser` class (~1150 lines):
- UI construction
- Directory scanning & metadata loading
- AppImage launching
- FUSE installation
- File monitoring
- Preferences/settings
- Cache management

### Proposed Module Structure

When refactoring into multiple modules, follow this architecture:

```
src/
├── core/
│   ├── AppImage.h/.cpp           # AppImage discovery, metadata parsing
│   ├── AppImageMetadata.h/.cpp    # Icon extraction, .desktop parsing, caching
│   └── FuseManager.h/.cpp         # FUSE2 detection, installer (platform-agnostic)
├── system/
│   ├── FileMonitor.h/.cpp         # Directory watching (GFileMonitor wrapper)
│   ├── ProcessManager.h/.cpp      # Subprocess execution, AppImage launching
│   └── Preferences.h/.cpp         # GSettings wrapper, preference persistence
├── ui/
│   ├── GTK3/
│   │   ├── UIBuilder.h/.cpp       # GTK3-specific UI construction
│   │   └── EventHandlers.h/.cpp   # GTK3 signal callbacks
│   ├── GTK4/
│   │   ├── UIBuilder.h/.cpp       # GTK4-specific UI construction
│   │   └── EventHandlers.h/.cpp   # GTK4 signal callbacks (gestures, etc.)
│   └── Common/
│       └── UIController.h/.cpp    # Shared UI orchestration logic
└── main.cpp                        # Entry point (minimal)
```

### Refactoring Strategy (Phase-Based)

**Phase 1: Extract Core Logic (No UI Changes)**
1. Create `src/core/AppImage.h` - `struct AppImage` + discovery functions
2. Create `src/core/AppImageMetadata.h` - metadata extraction, caching
3. Move `scan_directory()`, `load_metadata_async()`, cache logic here
4. Update both branches to use new core module
5. **Benefit**: Both GTK3 & GTK4 share identical core logic

**Phase 2: Extract System Services**
1. Create `src/system/FileMonitor.h` - wrap GFileMonitor, abstract platform details
2. Create `src/system/ProcessManager.h` - launch AppImage, FUSE detection
3. Move `start_dir_monitor()`, `launch_appimage()`, `has_fuse2()` here
4. **Benefit**: Testable, reusable, platform-independent

**Phase 3: Extract UI Layer**
1. Create `src/ui/Common/UIController.h` - non-rendering logic (state, callbacks)
2. Create platform-specific builders:
   - `src/ui/GTK3/UIBuilder.h` - GTK3 widget construction
   - `src/ui/GTK4/UIBuilder.h` - GTK4 widget construction
3. Move `create_ui()`, `populate_list()`, `build_appimage_tile()` to builders
4. **Benefit**: UI logic isolated, easy to swap renderers

**Phase 4: Centralize Preferences**
1. Create `src/system/Preferences.h` - GSettings wrapper
2. Encapsulate schema loading, key access
3. Both branches use identical Preferences API
4. **Benefit**: Settings logic testable, schema changes localized

### Refactoring Guidelines for LLMs

When refactoring this codebase:

**DO:**
- ✅ Extract pure functions first (e.g., `scan_directory` before UI)
- ✅ Create shared interfaces/abstract classes for platform-specific code
- ✅ Keep branch-specific code in separate files (e.g., `UIBuilder.h` per branch)
- ✅ Use dependency injection to pass services (FileMonitor, ProcessManager) to UI classes
- ✅ Write unit tests for extracted modules *before* integrating with UI
- ✅ Add `#pragma once` and comprehensive comments for module boundaries
- ✅ Update both branches when extracting shared modules
- ✅ Use const references and move semantics for performance

**DON'T:**
- ❌ Merge GTK3 and GTK4 code in the same file (branch divergence required)
- ❌ Extract UI without creating proper interfaces (leads to circular dependencies)
- ❌ Assume callback signatures remain stable (GTK3 vs GTK4 differ)
- ❌ Remove GSettings integration when extracting preferences
- ❌ Ignore platform differences in subprocess/file handling
- ❌ Create circular includes; use forward declarations

## API Reference for Both Branches

### AppImageBrowser Class Members (Current)

**Persistent Across Both Branches**:
```cpp
std::string current_directory;                    // Browsing location
std::vector<std::string> appimage_files;          // Flat list of AppImages
std::map<std::string, std::vector<std::string>> grouped_files;  // Grouped by folder
std::unordered_map<std::string, CachedInfo> cache_;  // Icon/metadata cache
GSettings* settings;                              // Preferences (GSettings)
bool group_by_folder;                             // Toggle: grouped vs flat view
```

**Methods to Preserve in Refactoring**:
- `scan_directory(const std::string& path)` - Find AppImages recursively
- `populate_list()` - Update UI based on current view mode
- `launch_appimage(const std::string& path)` - Execute AppImage
- `has_fuse2()` - Check FUSE2 availability
- `install_requirements()` - FUSE2 installer
- `load_metadata_async(const std::string& path, GtkWidget* button)` - Extract metadata

**Private Helpers** (can be extracted to modules):
- `find_desktop_file()` - Locate .desktop in extracted AppImage
- `parse_desktop_file()` - Extract Name, Comment, Icon from .desktop
- `get_cache_dir_for()` - SHA256-based cache directory path
- `extract_appimage_icon()` - Get .DirIcon or parse Icon= key

## Common Tasks & Branch Strategy

### Adding a New Feature

1. **Design phase**: Plan core logic (independent of UI framework)
2. **Implement on `main` (GTK3)**:
   - Add core logic to AppImageBrowser.cpp
   - Use GTK3 APIs for UI
   - Test thoroughly
3. **Port to `gtk4-libadwaita`**:
   - Port core logic (typically 80% reusable)
   - Update UI callbacks to GTK4 patterns
   - Test on GTK4 toolkit
4. **Commit strategy**:
   - `main`: Feature commit message
   - `gtk4-libadwaita`: Same commit message + "\n(GTK4 API updates)"

### Fixing Bugs

1. **If bug is in core logic** (AppImage discovery, metadata, preferences):
   - Fix on `main` first
   - Cherry-pick or manually apply to `gtk4-libadwaita`
   - Ensure both branches get the fix
2. **If bug is UI-specific**:
   - Fix on affected branch only
   - Document in commit why it's branch-specific

### Updating Dependencies

- **GTK3**: Edit `CMakeLists.txt` GTK3 section, test on main
- **GTK4/libadwaita**: Edit `CMakeLists.txt` GTK4 section, test on gtk4-libadwaita
- **GLib/GIO**: Both branches use same version; apply to both

## Git Workflow for Maintenance

### Syncing Core Changes Between Branches

When extracting modules or fixing shared logic:

```bash
# Work on main
git checkout main
# ... make changes to core logic ...
git commit -m "Extract AppImage scanning to core module"

# Apply to gtk4-libadwaita
git checkout gtk4-libadwaita
git merge main --no-edit  # If compatible
# OR manually apply changes + update UI
git commit -m "Extract AppImage scanning to core module (GTK4 UI updates)"
```

### Avoiding Large History

- ✅ Use `.gitignore` for `squashfs-root/`, `build/`, `node_modules/` (already in place)
- ✅ When cleaning history: `git filter-branch --tree-filter 'rm -rf dir' -- --all`
- ✅ After rewrite: `git reflog expire --expire=now --all && git gc --aggressive`
- ❌ Do NOT commit binary files, build artifacts, or test data

## Documentation for LLM Context

When working on this codebase, provide these instructions to the LLM:

1. **Always specify the branch**: "I'm working on the `gtk4-libadwaita` branch"
2. **Check API compatibility**: Use `pkg-config --list-all | grep gtk` to verify available versions
3. **Respect signal lifetime**: GTK3 uses gtk_signal_connect; GTK4 uses g_signal_connect with different signatures
4. **Cache coherency**: When modifying `cache_` map, ensure GFileMonitor callbacks stay in sync
5. **Thread safety**: `load_metadata_async()` spawns threads; GLib idle callbacks marshal back to main thread
6. **Async patterns**: GTK4 uses async APIs (GtkFileDialog); GTK3 uses blocking (GtkFileChooserDialog)
